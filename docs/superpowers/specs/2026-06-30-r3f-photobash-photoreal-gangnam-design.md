# R3F 포토배싱 포토리얼 강남 — 설계 스펙

- 날짜: 2026-06-30
- 상태: 승인됨 (브레인스토밍 게이트 통과)
- 브랜치: `feat/r3f-photobash-gangnam` (main에서 분기)

## 0. 한 줄 목표

**R3F metric 기하를 유일한 진실로 두고**, imagegen은 *소스 재료*로만 쓰며, imagegen에서 추출한 포토리얼 요소(건물 외관·간판·아스팔트·**닳은 차선/횡단보도/정지선 페인트**·하늘)를 **기하 좌표에 한땀한땀 데칼/텍스처로 합성**하여, **차선 정렬이 구조적으로 안 깨지는** 실사 강남 교차로(제한 오비트 3D, 주간 먼저)를 만든다.

## 1. 왜 (피벗 배경)

현재 구조는 imagegen "plate"(한 장짜리 2D 포토리얼 배경)가 base이고 metric R3F 기하가 그 위에 맞춰야 한다. imagegen이 도로 기하/차선을 미세하게 틀어 → 차선 정렬이 반복적으로 깨지고(`?plate=v5`는 R3F 차선 오버레이를 끄는 땜질, `plateVehicleCalibration` 오프셋 등 누적), 매번 보정의 악순환. **근본 원인: 한 장짜리 이미지의 내부 마킹 배치가 metric 기하와 다르다.**

## 2. 핵심 원리 (정렬이 안 깨지는 이유)

| | 옛 방식 (plate) | 새 방식 (포토배싱) |
|---|---|---|
| 포토리얼 출처 | imagegen | imagegen (동일) |
| 기하 출처 | **imagegen이 암묵적으로 결정** | **R3F 좌표가 100% 결정** |
| 마킹 | 한 장 이미지 안에 그려짐 | **개별 요소로 분해 → 정확한 metric 위치에 데칼 배치** |
| 정렬 | 이미지 전체가 한 번에 맞아야 함 (틀어짐) | **요소별로 각자 정확 위치에 앉음 (구조적으로 정확)** |

> **불변식(invariant): imagegen 출력은 절대 그대로 적용하지 않는다. 항상 추출 → metric 좌표에 합성.**

## 3. 역할 분담 (통합 모델)

- **R3F = 순수 기하 진실.** 건물 박스, 도로면, 차선 중심선/횡단보도 박스/정지선의 정확한 metric 좌표, 차량 위치, 신호, 제한 오비트 카메라. 자기만의 "그림"은 없음 — 좌표계 + 메시 + 표면 슬롯.
- **imagegen = 모든 포토리얼 외형의 소스.** 주간 강남 레퍼런스(건물 외관, 네온/간판, 아스팔트 노면, 마킹 페인트, 스카이라인). **바로 안 씀 — 추출 재료.**
- **합성가(나) = 추출 + 배치.** imagegen에서 요소를 잘라내 R3F 기하 좌표에 데칼/텍스처로 한땀한땀 정확히 얹고, 제한 오비트 렌더로 정렬/이음새 검증·미세조정.

## 4. 아키텍처 / 컴포넌트

### 4.1 기하 스켈레톤 (재사용 + 정확도 보강)
- 재사용: `intersectionTruth.ts`(좌표 진실), `roadGeometry.ts`, `buildingFootprints.ts`, 차량(`DynamicVehicleLayer`/`InstancedVehicleGlb`), 신호, SUMO/CCTV 바인딩.
- 보강: "완벽한 강남" 매스 — 건물 footprint·높이를 실제에 더 맞춤(필요 범위만).
- 카메라: 제한 오비트 리그(교차로 중심, 좌우 회전 + 줌/팬 + 고도 아크 제한). `CameraRig`에 클램프.

### 4.2 표면 요소 시스템 (신규 — 이 설계의 buildable 핵심)
"표면/요소마다 텍스처 슬롯을 두고 합성가가 추출 자산으로 채우는" 시스템:
- **건물 facade 슬롯**: 각 건물 메시 면에 facade 텍스처(주간) 슬롯.
- **간판/네온 요소**: 건물 면에 배치하는 emissive 텍스처 평면(개별 자산).
- **노면 텍스처 슬롯**: 도로 메시에 마킹 없는 아스팔트(교차로 전체 1장 고유 텍스처 권장 — 타일 반복 제거).
- **마킹 데칼 슬롯**: 차선/횡단보도/정지선을 **개별 데칼**로, 각자의 metric 좌표(차선 중심선, 횡단보도 박스, 정지선)에서 도로면 위에 배치. imagegen에서 추출한 닳은 페인트 텍스처 사용. (벡터 라인 아님)
- **백드롭 돔/스카이**: imagegen 스카이라인.
- 데이터 구조: 슬롯 매니페스트(요소 id → 자산 경로 + metric 변환[위치/회전/스케일] + 표면 바인딩). 합성가가 이 매니페스트를 채우고 미세조정.

### 4.3 추출/합성 워크플로 (도구)
- imagegen 소스 생성(주간 강남, 마킹/건물/노면/간판 레퍼런스).
- 추출: 크롭/세그먼트로 요소 자산화(투명 배경 PNG/webp).
- 배치: 슬롯 매니페스트에 metric 변환 입력 → R3F가 데칼/텍스처로 렌더.
- 검증: 제한 오비트 멀티뷰 렌더 → 정렬/이음새 점검 → 변환 미세조정(반복).

### 4.4 은퇴
- monolithic plate 시스템(`PhotorealPlate`, `BackgroundPlateLayer`, `plateProxyGeometry`, `plateCameraCalibration`, `plateVehicleCalibration`, `plateManifest`)을 이 표면별 요소 시스템으로 **교체/은퇴**. (락트 렌더링 가드레일·테스트는 교체에 맞춰 갱신; 인간 확인 게이트 거침.)

## 5. 단계화 (주간 MVP)

- **Phase 0 — 검증 슬라이스 (가장 중요):** 노면 아스팔트 텍스처 + **마킹 데칼(차선·횡단보도·정지선)을 metric 좌표에 배치** → 제한 오비트 렌더로 **차선 정렬이 정확함을 증명**. 이게 접근법 전체를 검증(옛 방식이 깨지던 바로 그 지점).
- **Phase 1 — 건물:** facade 텍스처 슬롯 + 간판 emissive 요소.
- **Phase 2 — 환경:** 스카이/백드롭, 조명/그림자 정합, 차량 위 정합.
- **Phase 3 — 폴리시:** 이음새·정렬 미세조정, verify 게이트 통과, plate 시스템 은퇴 마무리.
- (후속: 야간 — 동일 슬롯에 야간 자산 + emissive.)

## 6. 재사용 vs 은퇴 요약

- **재사용:** `intersectionTruth`/`roadGeometry`/`buildingFootprints`(기하), 차량·신호·SUMO/CCTV 바인딩, verify 하네스(`render-traffic-photoreal.mjs`/`render-plate-guides.mjs`는 멀티뷰 검증용으로 전용).
- **신규:** 표면 요소 슬롯 시스템 + 매니페스트, 마킹 데칼 레이어, 제한 오비트 카메라 클램프, 추출/배치 워크플로.
- **은퇴:** monolithic plate 6종.

## 7. 검증 / 게이트

- **시각 확인은 codex CLI로 컨펌 (필수 프로세스).** 렌더/정렬/이음새 같은 모든 시각 판단은 내 자체 image Read로 끝내지 않고 **`/home/chan/.local/bin/codex`에 넘겨 분석·컨펌**받는다. (프로젝트 선호: `visual-confirm-via-codex-cli`)
- **정렬 게이트(핵심):** 제한 오비트 다각도 렌더에서 마킹 데칼이 차량 궤적/차로와 일치(차로 폭 3.6m 정합) — **codex CLI 컨펌**으로 통과. Phase 0의 done-gate.
- 프로젝트 R3F 게이트: `cd apps/web && npx vitest run`, `npm run verify:r3f-dashboard`, `verify:r3f-visual-diff`(의도된 변경이니 rebaseline), `verify:r3f-performance`(~900 draw-call 예산), `verify:r3f-assets`(~25MB 예산), `verify:security`.
- 락트 렌더링(`apps/web/AGENTS.md`) 갱신은 인간 확인 게이트 후 반영.

## 8. 리스크 / 정직한 한계

- **이건 "파이프라인 한 번 돌리면 끝"이 아니다.** 추출→배치는 본질적으로 **합성가(나) 반복 작업.** 설계가 만드는 건 *그 작업을 가능·반복가능하게 하는 아키텍처(슬롯/매니페스트/데칼)*이고, 포토리얼 완성도는 반복 합성의 함수.
- **건물 facade 일관성:** imagegen 외관을 메시 면에 자연스럽게 맞추는 게 가장 손 많이 감. Phase 1에서 집중.
- **자산 예산:** 고유 노면/facade 텍스처가 25MB 예산을 압박할 수 있음 → 해상도/압축(webp) 관리.
- **draw-call 예산:** 다수 데칼/요소가 ~900 예산 압박 → 인스턴싱/아틀라스.
- **성공의 1차 척도는 Phase 0:** 마킹 데칼이 제한 오비트에서 차로와 정확히 맞으면 접근법 검증 완료.
